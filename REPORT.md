# ML-Based Memory Usage Prediction and Intelligent Cloud Resource Allocation

ACC lab CA — Cloud Resource Management · Author: Piyush

All numbers below come from `python main.py` (seed 42) and are reproduced in `results/RESULTS.md`.
**Scope note:** the workload is synthetic and the cluster is simulated with assumed cost/power figures; see Section 9.

## 1. Problem and objective

Cloud applications are normally provisioned either for their peak (wasteful) or reactively, adding capacity only after
load has already risen (risky, because new instances need time to launch and warm up). The goal is an ML-based
resource manager that predicts the memory demand of a service a short time ahead and sizes the instance pool for
that forecast, so capacity is ready *when* the demand arrives.

Objectives: (i) accurate short-horizon memory forecasts, (ii) an auto-scaling mechanism driven by them, (iii)
evaluation against static and reactive provisioning on accuracy, utilisation, latency, cost and energy, and (iv) a
study of failure behaviour when the forecast is wrong.

## 2. Input data and features

**Data.** 60 days at 5-minute resolution (17,280 rows): `requests` (req/s), `cpu_pct`, `memory_mb` (aggregate memory
demand of the service, 13-40 GB). The generator (`src/data_gen.py`) combines diurnal and weekly seasonality, 12 %
growth, AR(1) noise, ~1 traffic burst per day, a CPU signal proportional to requests, and memory = baseline + an
exponentially smoothed response to the request rate + a slow leak that resets at "deployments". Chronological split:
60 % train (≈35 days), 20 % validation, 20 % test (≈11.8 days); no shuffling. Any real trace can be loaded with
`--data` (Section 8).

**Features (32, all computed from data up to time *t*)** — verified leakage-free by a unit test:

* memory level; differences over 5 min … 24 h (lags 1, 2, 3, 6, 12, 36, 72, 144, 288 steps)
* rolling deviation-from-mean / std / deviation-from-max over 30 min, 1 h, 3 h
* the change over the same window *yesterday* (seasonal signal)
* request-rate level, differences, EMA and 3 h mean; CPU level and 15-min change
* calendar features of the *target* time (sin/cos hour, sin/cos weekday, weekend flag)

**Target.** The change in memory over the horizon, `memory(t+h) − memory(t)`; the prediction is added back to the
current memory. Predicting the change instead of the level keeps tree models from having to extrapolate past the memory
range seen in training (the trend pushes the test period above training levels).

## 3. Algorithm and prediction horizon

Candidates: persistence, 1-hour moving average, seasonal-naive (yesterday's change), Ridge regression, Random Forest,
Gradient Boosting (HistGradientBoosting) and an MLP (64-32). Models are fit on train, the best learned model is chosen
on validation MAE, then all are refit on train+validation and scored once on the test set.

| model | MAE (MB) | RMSE (MB) | MAPE | skill vs persistence |
|---|---|---|---|---|
| Persistence | 497.0 | 648.1 | 2.01 % | 0 % |
| Moving average (1 h) | 1249.5 | 1575.6 | 5.05 % | −151 % |
| Seasonal naive (24 h) | 436.8 | 597.5 | 1.75 % | 12 % |
| Ridge regression | 256.0 | 367.4 | 1.02 % | 48.5 % |
| Random Forest | 259.5 | 372.0 | 1.03 % | 47.8 % |
| Gradient Boosting | 260.5 | 371.8 | 1.03 % | 47.6 % |
| **MLP (64-32)** | **252.6** | **361.9** | **1.01 %** | **49.2 %** |

The four learned models are within ~3 % of each other, and a linear model is competitive; this is expected because the
synthetic memory is generated by (nearly) linear dynamics, so the table should not be read as evidence about which
family wins on real workloads. The MLP was selected by the validation rule. For the **upper bound** used for safety
headroom, a Gradient Boosting *quantile* model (q = 0.95) is trained; on the test set its coverage was **90.8 %**
(target 95 %), i.e. it is somewhat over-confident, plausibly because of the upward trend between training and test.
Permutation importance (`results/figures/04_feature_importance.png`) ranks the target-time hour, short-term changes in
request rate and the weekend flag highest.

**Horizon.** The default horizon is **15 min (3 steps)**, chosen to equal the assumed instance launch + warm-up time
(15 min): a decision taken now is only useful if it concerns the moment the new capacity becomes available. Sweep:

| horizon | 5 min | 10 min | 15 min | 30 min | 60 min |
|---|---|---|---|---|---|
| forecast MAE (MB) | 97 | 176 | 261 | 489 | 810 |
| persistence MAE (MB) | 179 | 340 | 497 | 942 | 1756 |
| cost, hybrid policy (USD) | 91.7 | 92.2 | 92.7 | 93.5 | 94.7 |
| steps with memory exhausted | 0 % | 0 % | 0 % | 0 % | 0 % |

Error grows roughly linearly with horizon and cost rises slightly (more headroom). On this smooth synthetic series,
horizons shorter than the launch delay did **not** cause violations, so the 15-minute choice rests on the launch-delay
argument rather than on a measured penalty.

## 4. Resource allocation / auto-scaling mechanism

Simulated service: instances of 4 GB memory, 15-minute launch + warm-up delay, 2-80 instances. At each 5-minute step:

1. **Sizing rule:** `instances = ceil(forecast(t+h) / (4096 MB × target_util))`, target utilisation 85 % by default.
   The forecast is the q95 upper bound for the predictive/hybrid policies.
2. **Scale-out is immediate** but capacity only arrives after the launch delay (billing and idle power start at launch).
3. **Scale-in is stabilised:** shrink only to the highest desired size seen in the last 30 min (anti-flapping). The
   same rules apply to every dynamic policy for fairness.
4. **Safety nets in the hybrid policy** (Section 7): emergency guard and drift fallback.

Policies compared: Static (training peak + 20 %, 12 instances); Reactive (same sizing rule but fed with *current*
demand, i.e. target tracking); Predictive-mean; Predictive-q95; Hybrid; and an Oracle that knows the true demand at
t+h (an upper bound on what any forecaster could achieve).

## 5. Evaluation metrics

*Accuracy:* MAE, RMSE, MAPE, R², skill vs persistence, under-prediction rate, q95 coverage. *Utilisation:* mean of
min(demand/capacity, 1). *Reliability:* % of steps where demand exceeds capacity (memory exhausted → OOM/swap), number
of such episodes, shortfall GB-hours. *Latency (proxy):* `40 ms / (1 − u)` capped at 20× below saturation, 2000 ms when
memory is exhausted; mean/p95/p99. *Cost:* billed instance-hours × $0.0416. *Energy:* per-instance power
45 W idle → 110 W at full utilisation (booting instances draw idle power). Prices, power and latency model are
assumptions, so absolute values illustrate relative differences only.

## 6. Results (test period, 85 % sizing target)

| policy | util | memory exhausted | p99 latency | cost | energy | avg instances |
|---|---|---|---|---|---|---|
| Static (peak-sized) | 50.3 % | 0 % | 194 ms | $141.36 | 264.0 kWh | 12.0 |
| Reactive | 78.6 % | 0.03 % (1 episode) | 333 ms | $90.95 | 209.5 kWh | 7.7 |
| Predictive (mean) | 78.5 % | 0 % | 279 ms | $90.95 | 209.5 kWh | 7.7 |
| Predictive (q95) | 77.0 % | 0 % | 255 ms | $92.71 | 211.4 kWh | 7.8 |
| Hybrid | 77.0 % | 0 % | 254 ms | $92.72 | 211.4 kWh | 7.8 |
| Oracle | 78.5 % | 0 % | 263 ms | $90.98 | 209.5 kWh | 7.7 |

* Any dynamic policy cuts cost by ≈36 % and energy by ≈21 % versus static peak sizing, at the price of higher latency
  (the cluster runs hotter, which the latency proxy penalises).
* At this operating point the differences between reactive and ML policies are small: the slow diurnal ramps are
  within what a 15 % headroom absorbs even with a 15-minute launch delay. The ML policies avoid the single short
  reactive violation and lower p99 latency, at equal cost for the mean forecast (+2 % for q95 headroom).

**Where prediction matters more — tighter packing.** Sweeping the sizing target (`results/target_util_sweep_*.csv`):

| target util | Reactive: violations / cost | Predictive-mean: violations / cost |
|---|---|---|
| 70 % | 0 % / $109.1 | 0 % / $109.1 |
| 85 % | 0.03 % / $91.0 | 0 % / $91.0 |
| 90 % | 0.06 % / $86.0 | 0 % / $86.1 |
| 95 % | 0.24 % / $82.1 | 0.03 % / $82.3 |

The forecast lets the cluster be packed tighter with fewer violations at nearly the same cost; the benefit is real in
this simulation but small in absolute terms (fractions of a percent of steps). Figures: `results/figures/05, 06, 10`.

## 7. What happens when the prediction is wrong?

Four experiments (figures 07, 08, 11):

**a) Systematic bias** (forecast multiplied by a constant; `wrong_prediction_bias.csv`). Forecasts 10 % too low are
still safe (0.03 % violations) because of sizing headroom; at −20 % the predictive-only policy leaves memory exhausted
in **28.9 %** of steps (121 episodes), at −40 % in essentially all steps. Over-prediction is safe but costly: +40 %
raises cost from $91 to $125 (+37 %) with no violations. **Under-prediction is the dangerous direction; over-prediction
only wastes money** — an asymmetry that argues for using an upper quantile rather than the mean.

**b) Random noise on the forecast** (`wrong_prediction_noise.csv`). Up to 20 % noise causes no violations (cost
rises $91 → $111 as the policy over-provisions on noisy up-swings); at 30 % noise predictive-only reaches 0.18 %
violations.

**c) Unforeseen memory surges** (+40 % for 90 min and +60 % for 60 min injected into the test period, requests
unchanged so no model feature can foresee them; `shock_scenario.csv`). Violations: Reactive 0.18 % (3 episodes),
Predictive and Hybrid 0.15 % (2 episodes), Oracle 0 %. **The safety nets did not help here:** the hybrid's emergency
guard and drift fallback did fire (fallback in 0.6 % of steps, guard in 0.2 %) but the new capacity still takes
15 minutes to arrive. The launch-delay sweep confirms the delay is the binding constraint: with the same forecasts,
violations of the predictive policy grow from 0.03 % (5-min launch) to 0.09 % (10), 0.15 % (15) and 0.41 % (30 min),
while the oracle goes from 0 % to 0.18 %.

**d) Drift fallback in the hybrid policy.** The hybrid compares each forecast with what actually happened h steps
later; if the mean absolute percentage error over the last hour exceeds 12 % it stops trusting the model and sizes
reactively with 30 % headroom. With a −20 % biased forecast the hybrid keeps violations at **0 %** (versus 28.9 % for
predictive-only) at a cost of $116 versus $93 for the unbiased hybrid — insurance paid for in cost. In the unbiased
run it never triggered (0 % of steps), so it caused no false alarms on this data.

**Mitigations discussed / implemented.** (1) forecast an upper quantile, not the mean (implemented); (2) monitor
realised forecast error and fall back to reactive sizing, and retrain when the error stays high (fallback implemented,
retraining trigger is the intended operational response but is not automated); (3) emergency guard on current
utilisation (implemented); (4) minimum-capacity floor and stabilised scale-in (implemented); (5) *not* implemented but
indicated by experiment (c): shorten effective launch time (pre-warmed pool, smaller images, containers) or keep
standing headroom, because no policy can react faster than capacity can be created; (6) application-level protection
such as memory limits and request shedding.

## 8. Cloud demonstration

The repository supports the demonstration on any cloud platform (instructions in `README.md` and `docs/DEMO_SCRIPT.md`):

1. Create a small VM (e.g. AWS EC2, GCP Compute Engine or Azure VM), clone the repo, `pip install -r requirements-cloud.txt`.
2. Run `python main.py` on the VM to reproduce the results (or use the `Dockerfile`).
3. Generate a real memory workload with `cloud/load_generator.py` and record it with `cloud/collect_metrics.py`
   (compressed-time option for demos), then retrain with `python main.py --data data/collected_vm.csv`.
4. Optionally apply the recommendation to an Auto Scaling Group with `cloud/aws_apply.py` (dry run by default) and
   publish the forecast as a CloudWatch custom metric to graph against actual memory.

*Status:* items 1-3 were exercised locally (including the `--data` path on the generated CSV); `aws_apply.py` was
only run in dry-run mode and has not been tested against a live AWS account. The screencast and any live-cloud
measurements are to be produced by the author on the chosen platform.

## 9. Limitations

* Synthetic data with a built-in "requests lead memory" relationship and near-linear dynamics: real traces are less
  predictable, so real accuracy will be lower and model ranking may change.
* Costs, power and latency use assumed parameters; the simulator ignores spot pricing, billing granularity,
  multi-dimensional resources (CPU, network), placement/bin-packing and application-level behaviour.
* One random seed and one test window; no confidence intervals. Differences between policies at the default operating
  point are small. The target-utilisation sweep was added after a first run at a 75 % target showed zero violations for
  every dynamic policy (no discrimination between them); results for all sweep points are reported, not just
  favourable ones.
* The q95 model is under-covered (90.8 %); a conformal calibration step would be a natural improvement.

## 10. Conclusion

Short-horizon memory forecasting (≈1 % MAPE here, about half the error of "no change") combined with an
upper-quantile sizing rule lets a cluster run at ≈78 % utilisation instead of ≈50 %, cutting simulated cost by about a
third and energy by about a fifth versus peak provisioning, with violation rates at or below those of a reactive
autoscaler. The experiments also show the limits: when forecasts are biased low the predictive-only policy fails
badly and needs the drift fallback, and when the surprise is a sudden surge the instance launch delay — not the
forecasting method — limits how well any policy can do.
